# Scope: 2026-Phase4 — AIMD dual-pressure (Concur+MARS+TokenScale 합성)

> L2: 승인 필요 | roadmap.md Phase 4 파생 | **Created**: 2026-05-09
> **Dependency**: Phase 1 + Phase 2 + Phase 3 완료 후 진행

## Change Summary

AIMD(Additive Increase Multiplicative Decrease) 동시성 제어를 Ollama VRAM 기반에서
llama-server slots_idle 기반으로 전환한다. 요청 부하에 따라 슬롯 수를 자동 조정하고,
슬롯 포화 시 같은 모델 추가 인스턴스를 **다른 LLM 노드** 또는 같은 노드(VRAM 여유 시)에 띄워 부하분산한다.

## AIMD ↔ ProcessManager 책임 경계 (핵심)

기존 AIMD 가 제대로 동작하지 못한 원인: 모델 적재(cold start) 시간을 부하 신호와 섞어 학습.
이번 단계에서 **모델 메모리 적재 영역(Phase 3)** 과 **AIMD 운영 영역(Phase 4)** 을 분리한다.

| 책임 | 단계 | 다루는 것 |
|------|------|-----------|
| Phase 3 ProcessManager | Stopped → Loading → Ready, Stopping → Stopped | 적재·해제·idle eviction |
| **Phase 4 AIMD** | **Ready 상태인 인스턴스만** | parallel 조정·scale-out·scale-in |

연결 지점:
- ProcessManager 가 Ready 진입 시 `AIMD.register(provider_id)` 호출
- ProcessManager 가 Stop 진입 시 `AIMD.unregister(provider_id)` 호출
- AIMD 는 Loading/Stopping 인스턴스를 **관측 대상에서 제외** (cold start 동안의 응답 지연으로 잘못된 학습 신호 생성 안 함)

## 현재 vs 새 AIMD

```
현재 (Ollama VRAM 기반):
  VRAM 잔량(MB) → 모델 로드 가능 여부 판단
  /api/ps 30s 폴링 → 갱신 지연 있음
  max_concurrent: LLM 배치 분석(30s 루프)으로 조정
  KV cache MB 단위 예약·해제

새 설계 (slots_idle 기반):
  slots_idle / (slots_idle + slots_processing) → 부하율 실시간 계산
  GET /health 즉시 응답 → 지연 없음
  AIMD: 부하율 > 0.8 → parallel++ (additive increase)
         에러율 증가  → parallel *= 0.5 (multiplicative decrease)
  슬롯 포화 + VRAM 여유 → 새 llama-server 인스턴스 시작 (scale-out)
  슬롯 포화 + VRAM 없음  → 큐에서 대기 (기존 Queue 활용)
```

## AIMD 상세 알고리즘 — Concur AIMD + MARS dual-pressure + TokenScale SLO

2026 논문 합성 (출처 명시). 기존 `slots_idle` 단일 신호 → **dual-pressure (KV + tool) admission window** 로 교체.

### 출처·이념

| 요소 | 출처 | 비고 |
|------|------|------|
| AIMD 룰·임계값 (α=2, β=0.5, U_low=0.2, U_high=0.5, H_thresh=0.2) | **Concur** (arXiv 2601.22705, 2026) | 검증 수치 직접 차용 |
| Dual-pressure 구조 (GPU memory + CPU/tool, both-healthy-for-increase) | **MARS** (arXiv 2604.26963, 2026) | 구조만 차용 (수치 누락) |
| SLO targets (TTFT 250/400/2000ms, TPOT 100ms) | **TokenScale** (arXiv 2512.03416, 2025-12) | 직접 차용 |
| Precise prefix cache aware routing (engine emit 구독) | **llm-d** (CNCF Sandbox, 2026-03) | 패턴 채택 |
| Multi-node 확장 | Logical extension | 논문은 single-node, Veronex 가 layer 위로 확장 |

### W (admission window) 정의

- **W**: router 측 동시 dispatch 한도, **0 < W ≤ n_parallel**
- llama-server `--parallel N` (engine 슬롯) 과의 관계:
  - W = N: AIMD 무작동 (full 사용)
  - **W < N: AIMD 백오프** (server 큐 누적 회피, 핵심 의의)
- 초기값: W = 1
- Max: W = n_parallel
- ProcessState ∈ {Stopped, Loading, Warming, Stopping} 시 신호 마스킹

### 신호 측정 (per-provider, 5s 주기)

```
GET /slots                                # llama-server, 단일 호출

# U_t — KV cache 사용률 (Concur U_t 의미 보존, llama.cpp 적합 측정)
U_t = Σ(slot.tokens for slot in slots) / (n_ctx × n_parallel)

# H_t — prefix cache hit 비율
#   Phase 1-3 prefix matcher 의 점수 재사용 (engine emit 구독 패턴, llm-d)
H_t = max(prefix_overlap(req.prompt, slot.prompt) for slot in slots)
      moving average 30s window

# T_t — MCP tool execution pressure (Veronex 고유, MARS CPU pressure 매핑)
T_t = mcp_tool_inflight / mcp_tool_capacity
      EMA(α=0.3) on tool execution duration
```

### 컨트롤 룰

```python
def update_window(W, control_interval=5s):
    # MARS dual-condition: 어느 한쪽이라도 overload → multiplicative cut
    if (U_t > 0.5 and H_t < 0.2) or T_t > 0.5:
        return max(1, W * 0.5)              # β=0.5 [Concur]
        # KV thrashing: 사용률 높지만 hit rate 낮음 — Concur 의도 보존
        # OR tool overload: MCP pipeline 포화 — MARS 추가

    # MARS both-healthy-for-increase: 양쪽 헤드룸 있을 때만 grow
    if U_t < 0.2 and T_t < 0.2:
        return min(W + 2, n_parallel)       # α=2 [Concur]

    return W                                 # neutral 영역 0.2 ≤ x ≤ 0.5
```

**임계값 출처:**
- U_low=0.2, U_high=0.5, H_thresh=0.2 — **Concur 권장**
- T_low=0.2, T_high=0.5 — Concur 비율 일관 차용 (MARS 누락분 보완)
- α=2, β=0.5 — **Concur 권장**
- control_interval=5s — LLM TTFT 측정 jitter 흡수, k8s HPA(15s) 보다 빠름 (LLM context 적합)

**민감도 노트** (Concur 검증):
- U_high 는 0.5~0.6 둔감 영역 — 0.5 안전
- U_low 는 정확 튜닝 필요 — admin 조정 가능 항목

### Cross-node Scale-out — TokenScale SLO 기반

```python
# SLO targets [TokenScale 직접 인용]
TTFT_SLO_MS = {
    'short':  250,    # < 256 input tokens
    'medium': 400,    # < 1024 input tokens
    'long':   2000,
}
TPOT_SLO_MS = 100   # all buckets

def should_scale_out(provider):
    bucket = classify_request_size(req)
    target_ms = TTFT_SLO_MS[bucket]
    return (
        ttft_p95_window(provider) > target_ms * 1.5     # 1.5× safety margin
        and sustained_for(30s)
    ) or (
        queue_depth(provider) > n_parallel              # router 큐 적체
        and sustained_for(15s)
    )

# 노드 선정 (Phase 3 capacity_status SSOT 재사용)
def pick_target_node(modelfile):
    candidates = nodes.filter(
        n.capacity_status == 'available'
        and n.gpu_accel.compatible_with(modelfile)        # Mac Metal vs Strix Vulkan
        and n.aggregate_load_ratio < 0.7
    )
    if candidates:
        return max(candidates, key=lambda n: n.free_unified_memory_mb)
    record_event('all_nodes_saturated')
    return None
```

**1.5× safety margin 과 30s sustained 는 운영 디폴트** (논문 직접 인용 X). 향후 TokenScale proactive 철학으로 1.0× 까지 낮출 수 있음.

### Prefix cache 시딩 (Cross-node scale-out 시)

기존 인스턴스의 hot prefix(자주 적중되는 system prompt 등)를 새 인스턴스에 미리 주입:

```
1. 기존 인스턴스에서 prefix_cache_hit_ratio 가장 높은 N개 prefix 추출
   GET {existing}/slots → prompt 토큰 + 적중 통계
2. 새 인스턴스에 짧은 dummy 호출로 cache warmup
   POST {new}/v1/chat/completions { messages: [system: {prefix}], max_tokens: 1, cache_prompt: true }
3. 이후 실 트래픽 라우팅 → 새 인스턴스도 prefix hit 즉시 가능
```

→ scale-out 직후 새 인스턴스의 TTFT 페널티 큰 폭 완화.

### ETA 정확도 (cold start 시간 예측)

`mincore(2)` page cache 잔존도 → cold disk 가 cold start 의 지배 요인:

```
estimate_cold_start(model_path, history) =
   base = size_gb * pagecache_factor + 5s
   pagecache_factor:
     resident_pages_ratio >= 0.9 → 0.5    (디스크 hit, 빠름)
     resident_pages_ratio >= 0.5 → 1.0
     resident_pages_ratio < 0.5  → 2.5    (cold disk, 느림)
   ema_blend = 0.7 × base + 0.3 × history_p50
```

resident_pages_ratio 는 `mincore(2)` 시스템콜로 계산.
ClickHouse `cold_start_events` 에 기록 → 같은 model 이력 누적.

```
같은 model 요청:

```

노드 선정 기준 (scale-out 시 어느 노드에 띄울지):
1. **GPU 벤더 호환성** — 모델 GGUF 가 해당 노드 가속 백엔드(CUDA/Metal/ROCm)에 호환

3. 노드 aggregate load_ratio 가장 낮음 (해당 노드 모든 Ready 프로세스 평균)

### 4-1. Snapshot/Restore — Sub-second cold start

**원리**: CRIU + CUDA Checkpoint API 결합. Modal 2.5×, vLLM RFC 10× 검증된 패턴.

```
Ready + Warmup 통과 직후:
  1. 백그라운드 snapshot:
     - CRIU dump (process state, mmap, fds)
     - CUDA Checkpoint API (GPU memory state)
     - macOS: process suspend + mach VM dump (제한적, NVIDIA 만큼은 아님)
  2. 노드 로컬 NVMe 저장:
     /var/veronex/snapshots/{model_hash}/{driver_hash}_{cuda_ver}_{gpu_arch}.snap
  3. snapshot 메타 DB 등록 (호환성 키)

ensure_running 진입 시:
  - snapshot 존재 + 호환 (driver/CUDA/GPU arch 매칭) → restore (목표 2~5s)
  - 호환 안 되거나 없음 → clean load (Loading→Warming→Ready 30~60s)

호환성 규칙:
  driver_hash = sha256("{nvidia-driver-version}_{cuda-runtime}_{arch}")
  driver 마이너 업데이트 → snapshot 무효화 (stale)
```

**모듈**:
```

├── criu.rs              # CRIU 명령 래퍼 (Linux), dump/restore/diff
├── cuda_checkpoint.rs   # NVIDIA CUDA Checkpoint API (cudaCheckpointProcessLock 등)

├── compatibility.rs     # driver_hash, cuda_ver, gpu_arch, model_hash 매칭
├── store.rs             # NVMe 저장 + LRU eviction (디스크 한계 시 오래된 snapshot 삭제)
```

### 4-2. Lease — 다중 router replica HA

**원리**: PostgreSQL advisory lock 기본, etcd 옵션. 두 router replica 가 같은 provider 동시 시작 방지.

```
ProcessManager.ensure_running(provider_id):
  1. lease.try_acquire(provider_id, ttl=30s)
     - 성공 → 시작 진행
     - 실패 → 다른 replica 가 시작 중 → 503 폴링 응답
  2. 시작 중 백그라운드: lease.renew(provider_id) every 10s
  3. Ready 진입 시 lease.release(provider_id)

장애 시: TTL 만료 → 다른 replica 가 lease 획득해서 재시작 (자동 복구)
```

### 4-3. Predictive Autoscaling — Load Forecaster (SCOOT 영감)

**원리**: 반응적(reactive) AIMD 만으로는 SLO 위반 후에야 대응 → 사전 예측으로 pre-warm.
SCOOT (Bayesian forecasting + constraint pruning) 패턴 채택, EMA+Holt-Winters 로 구현 (lightweight).

```
ClickHouse inference_request_events 시계열 (model × 노드별):

1분 주기:
  history = last 24h request rate (1min buckets)
  forecast = predict_next_5min(history)

  // EMA 단기 트렌드 (α=0.3, 5min window)
  ema_forecast = α · last_obs + (1-α) · prev_ema

  // Holt-Winters 계절성 (24h hour-of-day pattern)
  hw_forecast = level + trend + seasonal_24h[hour_of_day]

  // Blend: 단기 트렌드 우세 + 일별 패턴 보정
  blend = 0.7 · ema + 0.3 · hw

# SCOOT-style constraint pruning:
# pre-warm 후보를 SLO·예산·노드 가용성으로 가지치기
candidates = nodes_with(capacity_status='available')
            .filter(n => n.gpu_accel.compatible_with(modelfile))
            .filter(n => budget_check(n))     # 운영자 정의 (선택)

if forecast > current_capacity × 0.7 and candidates non-empty:
  pre_warm = ProcessManager.load_model(target_node, config)
  // 트래픽 도달 전에 이미 Ready
```

**Blend 비율 (0.7 EMA + 0.3 HW)**: 운영 디폴트. 24h 데이터 누적 전엔 EMA 만 사용 (HW=0).

**모듈**:
```
infrastructure/outbound/forecast/
├── ema_forecaster.rs           # 지수이동평균
├── holt_winters_forecaster.rs  # 계절성 (24h 주기)
├── ts_repository.rs            # ClickHouse 시계열 read (per-model, per-node, 1min bucket)
└── manager.rs                  # LoadForecaster 본구현 (blend EMA + HW)
```

**DB**: 기존 ClickHouse `inference_request_events` 활용 (별도 추가 없음).

### 4-4. Tiered KV Cache — GPU → CPU pinned → NVMe

**원리**: KV cache 가 GPU 메모리 압박의 주범. tiered 오프로딩으로 effective context capacity 확장.

```
llama-server 옵션 활용:
  --cache-type-k q8_0 / f16   # KV 양자화 (메모리 50%~75% 절감)
  --cache-reuse N             # prompt prefix 재사용 토큰 수
  --no-mmap (기본 off)        # 큰 모델은 mmap 끄기 옵션화

CPU pinned 오프로드: llama-server 가 GPU 슬롯 부족 시 CPU 메모리에 KV 보관
                     (GPU layers 외 KV 가 CPU 로 자동 이동)

NVMe 오프로드: prefix_seeder 와 결합 — 인스턴스간 prefix 시드 채널이 NVMe 기반 prefix store
  - 노드 로컬 NVMe: /var/veronex/prefix_cache/{model_hash}/{prefix_hash}.bin
  - 같은 모델 다른 인스턴스가 시작될 때 NVMe 에서 prefix 읽어 cache_prompt 시드
```

**모듈**:
```

├── llama_server_kv.rs    # /props 통한 KV 설정 조회 + --cache-type-k/v 매핑
```

### 4-5. Criticality Classes — interactive vs batch

**원리**: 요청 우선순위로 cache locality + TTFT/throughput 트레이드오프 분리.

```
ALTER TABLE inference_jobs ADD COLUMN criticality TEXT NOT NULL
  DEFAULT 'interactive' CHECK (criticality IN ('interactive', 'batch'));

요청 헤더: X-Criticality: interactive|batch
또는 api_keys.default_criticality

router 분기:
  interactive:
    - Ready 인스턴스만 즉시 dispatch
    - Stopped/Loading → 503 + Retry-After (앞서 결정한 정책)
    - prefix-aware 라우팅 그대로
  batch:
    - Loading 중에도 큐에 holding 가능 (최대 5min)
    - 같은 인스턴스 sticky (cache hit 최대화)
    - p95 TTFT 목표 완화 (예: 30s 까지)
    - AIMD scale-out 트리거에서 batch 비중 차감 (interactive SLO 보존)
```

**DB / 어드민**:
```sql

```

### 4-6. Cross-node Scale-in (single-instance fleet 정리)

**원리**: 같은 모델이 여러 노드에 떠있을 때, 전체 fleet load 가 낮아지면 정리.

```
fleet sync (5min 주기):
  for each model with instance_count > 1:
    fleet_load_ratio = avg(pressure_signal across instances)
    if fleet_load_ratio < 0.4 sustained 5min:
      // 가장 늦게 추가된 cross-node 인스턴스 종료 (원본 보존)

                          .order_by(created_at DESC)
                          .first()
      if candidate.is_some():
        ProcessManager.stop(candidate.id)
        record_event("fleet_scale_in")

원본 인스턴스 idle 종료는 Phase 3 IdleManager 가 담당 (idle_ttl).
```


## 스마트 모델 선택 (요청 증가 시)

```
요청 모델이 현재 미로드 상태일 때:
  1. VRAM 확인: 이 모델 올릴 공간 있나?
     있음 → ProcessManager.load_model()
     없음 → 어떤 모델 내릴까?

  2. 모델 교체 우선순위 (AIMD 정보 활용):
     - slots_processing == 0 이고 last_request가 가장 오래된 모델 선택
     - 해당 모델 프로세스 종료 (graceful, 진행 중 요청 완료 후)
     - 새 모델 시작

  3. 대기 큐 처리:
     로드 완료 → 대기 중이던 요청 자동 dispatch
```

## Completion Criteria

- [ ] **Composite pressure signal** (queue_depth × 0.5 + slots × 0.3 + TTFT_breach × 0.2) 동작
- [ ] **SLO 기반 cross-node 트리거** (p95_TTFT > target × 1.5 30s OR queue_depth > N 15s)
- [ ] **Prefix cache 시딩** — scale-out 시 hot prefix top-3 새 인스턴스 주입
- [ ] **ETA 정확도** — `mincore(2)` page cache 잔존도 반영 + ClickHouse 이력 EMA
- [ ] **AIMD 는 ProcessState::Ready 인스턴스만 관측** (Loading/Warming/Stopping 제외)
- [ ] **on_ready / on_stopped 훅** — Warmup 통과 후에만 AimdRegistry.register
- [ ] AIMD additive increase / multiplicative decrease 동작
- [ ] Cross-node scale-out **GPU 벤더 호환성 검증** 통과 (NVIDIA/AMD/Apple Metal)
- [ ] 같은 모델 다중 인스턴스 cross-node 부하분산 (Phase 1 prefix-aware 라우팅)
- [ ] scale-in (다중 인스턴스 한정)
- [ ] VramPool → SlotPool 단순화
- [ ] ClickHouse capacity_events 기록 (node_id, model, gpu_vendor 포함)
- [ ] **Snapshot/Restore 본격 구현** — CRIU + CUDA Checkpoint, restore 시 cold start 2~5s 검증
- [ ] **Lease 본격 구현** — pg_advisory_lock 기반, 다중 router replica 시 동시 시작 방지 검증
