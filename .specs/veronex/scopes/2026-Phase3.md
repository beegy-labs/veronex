# Scope: 2026-Phase3 — ProcessManager (lazy 라이프사이클 + 다중 노드)

> L2: 승인 필요 | roadmap.md Phase 3 파생 | **Created**: 2026-05-09 | **Updated**: 2026-05-09
> **Dependency**: Phase 1 + Phase 2 완료 후 진행

## Change Summary

llama-server 바이너리 설치·프로세스 시작/중지/모니터링을 Veronex가 직접 관리한다.
Phase 1: URL 등록(외부 서버 가정) → Phase 3: **lazy 라이프사이클 + 다중 LLM 노드 운영**.

라이프사이클(managed 모드):
1. 추론 요청 라우팅 시 대상 모델 프로세스 미기동 → ProcessManager 자동 시작
2. 활동 추적: 마지막 요청 종료 시각 갱신
3. 유휴 N초(기본 60s, 어드민 변경) 또는 명시적 unload API → 프로세스 종료

LLM 노드 추상화: Veronex 본체 호스트 + 원격 베어메탈 LLM 노드(직접 설치) 모두 지원.
external 모드 provider는 본 라이프사이클 비대상 (Phase 1 호환).

## 핵심 플로우

### A. Lazy start — 추론 요청 트리거 (Modelfile + 503 정책)

```
추론 요청 라우팅
  │
  ├── 1. Modelfile lookup (Phase 2 veronex_models)
  │      - model="qwen3-coder:q4_K_M"  → 정확 row
  │      - model="qwen3-coder"          → is_default=true row
  │      - 없음 → 404 { error: "model_not_registered",
  │                    message: "Register via POST /v1/admin/models" }
  │
  ├── 2. install_status 가드 (Phase 2 install FSM 과 통합)
  │      ├── ready                                 → 진행
  │      ├── pending|downloading|uploading|verifying
  │      │     → 503 + Retry-After + status_url
  │      │     body: { reason: "model_installing", attempt_no, stage, progress_pct,
  │      │             status_url: "/v1/admin/models/{id}/install/stream" }
  │      └── failed                                → 409 Conflict
  │            body: { reason: "install_failed", error_kind, error_message,
  │                    retryable, retry_url: "/v1/admin/models/{id}/install/retry" }
  │
  ├── 3. pick_best_provider(modelfile.blob_sha256) → managed provider 선택
  │      (Phase 1: prefix-aware + slots_idle, Phase 4: AIMD composite)
  │
  ├── 4. ProcessState 분기:
  │      │
  │      ├── ProcessState::Stopped:
  │      │     a. ProcessManager.ensure_running(model_id) — 비동기 트리거 (idempotent)
  │      │        → 백그라운드:
  │      │           - ModelStore.resolve_blob(modelfile.blob_sha256)
  │      │             → Local PV /blobs/{sha256}.gguf 확인
  │      │             → 없으면 Garage 에서 streaming → atomic write
  │      │           - spawn llama-server (모든 runtime params 는 Modelfile 에서)
  │      │           - /health 폴링 → Warming → Ready
  │      │     b. 503 Service Unavailable 즉시 응답:
  │      │        Retry-After: {eta_seconds}
  │      │        body: { reason: "model_loading", model_id, provider_id,
  │      │                eta_seconds, progress: 0.0,
  │      │                status_url: "/v1/inference/status?model={model_id}" }
  │      │
  │      ├── ProcessState::Loading (다른 요청이 이미 트리거 중):
  │      │     동일 503 응답 (ensure_running idempotent)
  │      │     progress · eta 는 ActivityTracker + 시작 시각으로부터 계산
  │      │
  │      └── ProcessState::Ready:
  │            ├ 즉시 dispatch (WARM PATH)
  │            ├ activity_tracker.on_request_start(provider_id)
  │            └ adapter.infer / stream_tokens (chat_template + defaults 적용)
```

**install_status 와 ProcessState 의 분리**:
- `install_status` = Modelfile/blob 의 등록·다운로드·검증 상태 (Phase 2)
- `ProcessState` = llama-server 프로세스 lifecycle (Phase 3)
- 둘은 직교: `install_status='ready' && ProcessState::Stopped` 이면 lazy start 가능
- `install_status != 'ready'` 이면 ProcessManager 진입 자체 차단

**큐 holding 정책 폐기**: 이전 안의 30s 큐 보류 → 즉시 503 으로 변경. 이유:
- 클라이언트(웹/모바일)에 "모델 설정중" UX 노출 가능 (spinner + ETA + progress)
- HTTP 커넥션 점유 회피 (cold start 30~120s 동안 idle 커넥션)
- OpenAI 호환 SDK 의 `Retry-After` 자동 백오프 활용

**ETA 계산**: 첫 진입 시 모델 크기 기반 휴리스틱 (`size_gb * 1.0s + 5s` 정도), 이후 같은 model 의 과거 cold start 평균으로 갱신.

### B. 모델 상태 조회 (Loading 중 클라이언트 폴링/구독)

```
GET /v1/inference/status?model={model_id}
  → { status: "ready" | "loading" | "stopped" | "failed",
      provider_id, node_id, model,
      progress: 0.0~1.0, eta_seconds,
      started_at, ready_at?, error? }

GET /v1/inference/status/stream?model={model_id}      (SSE)
  → 상태 전이 이벤트:
    data: {"event":"loading","progress":0.4,"eta_seconds":12}
    data: {"event":"ready","provider_id":"...","ready_at":"..."}
    (ready 또는 failed 시 스트림 종료)
```

이 두 엔드포인트로 클라이언트는 폴링 또는 SSE 중 선택해서 "모델 설정중 → 준비 완료" 전이를 관측 가능.

### C. 명시적 load API (운영자 사전 로드)

```
POST /v1/inference/load { model_id, node_id? }
  │  (model_id = Phase 2 veronex_models PK, runtime params 는 Modelfile 에서 자동)
  │
  ├── 1. Modelfile lookup → install_status 검증 (ready 아니면 409/503)
  ├── 2. ModelStore.resolve_blob(modelfile.blob_sha256) → Local PV path
  │     → 없으면 Garage 에서 fetch (streaming, sha256 검증)
  ├── 3. 노드 선정 (node_id 명시 또는 capacity_status='available' 인 노드 자동 선택)
  ├── 4. ProcessManager.start_on(node, model_id, blob_path, modelfile.runtime)
  │     → 바이너리 확인 (없으면 자동 설치, 노드별)
  │     → 포트 할당, spawn, /health 폴링, warmup → Ready
  ├── 5. LlmProvider DB 자동 등록 (mode='managed', node_id, model_id)
  └── 6. 응답: { provider_id, node_id, port, status: "running" }
```

**참고**: `hf_repo`/`quantization`/`ctx_size` 등은 더 이상 load API 입력이 아님.
  - 모델은 Phase 2 에서 미리 등록되어야 함 (404 if 미등록).
  - runtime params (n_ctx, n_gpu_layers, flash_attn, ...) 는 Modelfile.runtime 에서 자동.
  - 변경하려면 PATCH /v1/admin/models/:id (runtime 필드만 수정 시 재다운 없음).

### D. Idle eviction — 자동 종료

```
IdleManager 루프 (5s 주기):
  for provider in managed_running:
    idle_for = max(now - last_request_at,
                   now - last_request_completed_at)
    if idle_for >= idle_ttl_seconds (기본 60s, system_settings):
      ProcessManager.stop(provider_id)
        → AIMD 추적 해제 (Phase 4)
        → SIGTERM → 5s → SIGKILL
        → port_pool.release()
        → DB status='stopped'

명시적 unload API: DELETE /v1/inference/{provider_id}
  → 동일 stop 경로 (idle 무관 즉시 종료)
```

### LLM 노드 (지원 매트릭스 — Mac M-chip + AMD AI 395+ 전용)

llama-server 는 두 종류의 호스트에 직접 설치/운영. 처음부터 **N개 노드 가정**으로 설계.

#### 지원 매트릭스 (좁힘)

| 타깃 | OS / Arch | GPU | 가속 백엔드 | 빌드 플래그 | 배포 형태 |
|------|-----------|-----|-------------|------------|-----------|
| **Apple M-chip** | macOS / aarch64 | Apple Metal (M1/M2/M3/M4) | Metal | `cmake -DGGML_METAL=ON` | 베어메탈 (k8s 미운영, agent 네이티브 spawn) |
| **AMD AI 395+** | Linux / x86_64 | Radeon 8060S iGPU (Strix Halo, gfx1151) | **Vulkan (RADV)** | `cmake -DGGML_VULKAN=ON` | k8s 워커 노드 |

**제외:**
- NVIDIA CUDA — 이번 라운드 제외 (필요 시 별도 Phase 에서 추가)
- Intel Mac — 미지원
- AMD 일반 dGPU·CPU only — 미지원
- AMD ROCm 백엔드 — Strix Halo 공식 미지원 (tier 2), KV cache 공유 메모리 dump 버그, ROCm 7 nightly 64GB 메모리 cap 버그. **Vulkan 이 prompt processing + token gen + MoE 모든 영역 우세**.

#### Apple M-chip (베어메탈)

- M1/M2/M3/M4 모두 unified memory 아키텍처 → 큰 모델 mmap 유리
- llama.cpp `GGML_METAL=ON` 빌드 → `.dylib` (`ggml-metal.metal` 셰이더 동봉)
- agent 가 호스트에서 직접 spawn (Mac 은 k8s 운영 비현실적)
- GPU 메트릭: `ioreg -l | grep IOAccel*` + `powermetrics --samplers gpu_power`

#### AMD AI 395+ (k8s 워커 노드)

**APU 구조** — dGPU 옵션 없음, Radeon 8060S iGPU 가 유일 GPU. dGPU 와의 차이:
- 메모리 구조: 통합 LPDDR5X-8000 256 GB/s, 최대 128 GB
- GPU 가시 영역: 약 96 GB (boot param 조정 필요)
- 강점: 70B 모델 q4_K_M 도 통째 mmap 가능 (~45 GB), dGPU 로는 불가능한 영역

**필수 호스트 설정** (gitops `platform-gitops` 의 노드 부트스트랩 책임):
```
boot params: iommu=pt amdgpu.gttsize=126976
  - amdgpu.gttsize: GTT (Graphics Translation Table) 크기 (KiB 단위)
  - 126976 KiB ≈ 124 GiB → GPU 에 노출되는 unified memory 풀
  - 미설정 시 기본값 cap 으로 대형 모델 로드 실패
```

**K8s 컨테이너 측면:**
- AMD GPU Operator·k8s-device-plugin 불필요 (Vulkan 경로)
- Pod spec: `/dev/dri` (renderD128 + card0) hostPath 마운트
- agent 컨테이너 이미지: Mesa + RADV Vulkan ICD 포함 (Ubuntu 24.04+ / Fedora 42+ 권장)
- Pod 권한: `securityContext.privileged: false`, `runAsUser: 0` 불필요 — `video`/`render` 그룹만

**예상 성능 (단일 노드):**
- 30B q4_K_M: 40+ tok/s
- 70B q4_K_M: 30+ tok/s (모델 따라)
- MoE (gpt-oss 120B 등): 65-87 tok/s
- 메모리 대역폭 활용 70-73% / 256 GB/s 이론치

### LLM 노드 capacity_status 판정

각 노드의 새 모델 수용 가능성을 한 눈에 표시하기 위한 3단계 상태:

| status | 조건 | 의미 | scale-out / load 후보 여부 |
|--------|------|------|----------------------------|
| `available` | `free_vram_mb >= avg_loaded_model_size_mb * 1.3` (또는 노드에 인스턴스 0) | 새 모델 즉시 로드 가능 | ✅ 우선 후보 |
| `in_use` | 일부 사용 중이지만 작은 모델은 수용 가능 (`free_vram_mb >= MIN_MODEL_SIZE_MB`, 기본 4096) | 부분 사용 — 큰 모델은 불가, 소형 모델만 가능 | ⚠ 모델 크기 검증 후 |
| `saturated` | `free_vram_mb < MIN_MODEL_SIZE_MB` 또는 GPU 온도 임계 초과(Thermal 게이트) | 더 이상 신규 할당 불가 | ❌ 후보 제외 |

`capacity_reason` 은 사람이 읽을 수 있는 설명 (예: `"3 instances, 2.1GB free of 24GB"`, `"thermal gate: GPU0 89°C"`).
Phase 4 의 `node_selector.pick_node_with_capacity()` 가 동일 기준 사용 — UI 표시와 라우팅 결정의 일관성 보장.

```
infrastructure/outbound/process_manager/
├── mod.rs
├── binary.rs           # llama-server 바이너리 관리 (노드별)
│   - check_installed(node) -> bool
│   - install(node, version) -> Result   (GitHub Releases API, remote 면 agent 위임)
│   - binary_path(node) -> PathBuf
│   - LLAMA_SERVER_VERSION 상수
├── process.rs          # 프로세스 생명주기 (단일 인스턴스)
│   - ProcessState { Stopped, Loading, Warming, Ready, Stopping, Failed }
│   - LlamaServerProcess { provider_id, node, port, state, started_at, ready_at, config }
│   - start(node, config) -> Result<Self>
│   - stop() -> Result
│   - health() -> SlotStatus
│   - wait_healthy(timeout) -> Result    (Stopped → Loading → Warming → Ready 전이)
├── warmup.rs           # 첫 진짜 요청 TTFT 스파이크 제거 (TGI 패턴)
│   - run_warmup(process) -> Result
│   - 합성 프롬프트 2개:
│       1) 짧은 프롬프트 ("Hello, respond with a single word.")  — CUDA graph 캡처
│       2) 75% n_ctx 길이 프롬프트                              — 큰 시퀀스 경로 캡처
│   - 둘 다 max_tokens=8 으로 제한 (시간 절약)
│   - 성공 시 Warming → Ready, 실패 시 Failed
├── port_pool.rs        # 포트 관리 (노드별)
│   - allocate(node) -> u16 (11430~11530 범위)
│   - release(node, port)
├── activity_tracker.rs # 활동 추적
│   - touch(provider_id, kind: RequestStart | RequestEnd)
│   - idle_for(provider_id) -> Duration
│   - on_stop(provider_id)  (정리)
├── idle_manager.rs     # 유휴 자동 종료 루프
│   - tick() — 5s 주기
│   - idle_for >= settings.idle_ttl → manager.stop(provider_id)
└── manager.rs          # 전체 오케스트레이터
    - ProcessRegistry: DashMap<ProviderId, LlamaServerProcess>
    - ensure_running(model_id) -> Result        (lazy start 진입점, 라우터에서 호출)
                                                 (내부: Modelfile lookup → blob_sha256 → ModelStore.resolve_blob)
    - load_model(node, modelfile) -> Result<LlmProvider>   (명시적 사전 로드)
                                                 (모든 runtime params 는 modelfile.runtime 에서)
    - stop(provider_id) -> Result               (idle/unload/명시 모두 동일 경로)
    - on_ready(provider_id) → AIMD.register     (Phase 4 연동)
    - on_stopped(provider_id) → AIMD.unregister (Phase 4 연동)
    - list_running() -> Vec<ProcessInfo>
    - auto_recover()                            (프로세스 크래시 감지 + 재시작)
```

## llama-server 시작 파라미터 (Modelfile.runtime 에서 매핑)

```bash
llama-server \
  --model {local_pv}/blobs/{blob_sha256}.gguf   # CAS path (Phase 2)
  --ctx-size      {runtime.n_ctx}                # 기본 32768
  --parallel      {runtime.n_parallel|2}         # AIMD 가 조정 (Phase 4)
  --port          {port}                         # port_pool 할당
  --host 127.0.0.1
  --gpu-layers    {runtime.n_gpu_layers}         # -1 = 전부 GPU
  --batch-size    {runtime.n_batch|512}
  --threads       {runtime.n_threads|auto}
  $(if runtime.flash_attn) --flash-attn
  --split-mode    {runtime.split_mode|layer}
  --cache-type-k  {runtime.cache_type_k|f16}     # Phase 4 Tiered KV 와 연동
  --cache-type-v  {runtime.cache_type_v|f16}
  $(if runtime.rope_freq_base) --rope-freq-base {...}
  $(if runtime.rope_freq_scale) --rope-freq-scale {...}
```

**chat_template / stop_tokens / system_prompt / defaults** 는 추론 요청 시 라우터에서 적용 (llama-server CLI 가 아님).
요청 단위 override 가능 (defaults 는 클라이언트가 덮어쓸 수 있음).

원격 노드 실행: `veronex-agent` 가 동일 명령을 위임 실행하고 stdout/stderr 스트림 + /health 프록시 제공.

## 새 API 엔드포인트

```
# 명시적 사전 로드 (선택 — lazy 라이프사이클로도 자동 시작됨)
POST /v1/inference/load
     { model_id, node_id? }
     → 202 { job_id }  (모델 로드 시작, SSE로 진행 확인)
     node_id 미지정 시 capacity_status='available' 노드 자동 선정 (Phase 4 node_selector)
     model_id 미등록 → 404, install_status != 'ready' → 503/409

GET  /v1/inference/load/{job_id}/status
     → { phase: "downloading|starting|ready|failed", progress... }

# 명시적 unload — idle eviction 과 동일 경로
DELETE /v1/inference/{provider_id}
     → 프로세스 종료 + AIMD 추적 해제 + DB status='stopped'

GET  /v1/inference/running
     → 현재 실행 중인 llama-server 목록 (provider_id, node_id, pid, port,
                                       model, slots, last_request_at, idle_for_s)

# 모델 상태 조회 (Loading 중 클라이언트 안내용)
GET  /v1/inference/status?model={model_id}
     → { status, provider_id, node_id, model, progress, eta_seconds,
         started_at, ready_at?, error? }

GET  /v1/inference/status/stream?model={model_id}    (SSE)
     → loading/ready/failed 전이 이벤트, ready 또는 failed 시 종료

# 활성 모델 / 노드 capacity 요약 (어드민 대시보드용)
GET  /v1/admin/inference/summary
     → {
         total_active_instances: u32,                    # 전체 Ready 인스턴스 수
         total_models_active: u32,                       # 고유 모델 종류 수
         by_model: [
           { model, instance_count, total_slots_idle,
             total_slots_processing, nodes: [node_id...],
             aggregate_load_ratio }
         ],
         by_node: [
           { node_id, name, host, role,
             gpu_count, total_vram_mb, used_vram_mb, free_vram_mb,
             instance_count, models: [model...],
             aggregate_load_ratio,
             capacity_status: "available" | "in_use" | "saturated",
             capacity_reason }
         ]
       }

GET  /v1/admin/inference/summary/stream                  (SSE, 5s 주기 갱신)
     → 동일 payload, 대시보드 라이브 업데이트용

# LLM 노드 관리 (어드민)
POST   /v1/admin/nodes               { name, host, role, agent_url?, gpu_count }
GET    /v1/admin/nodes
DELETE /v1/admin/nodes/{node_id}

# 시스템 설정 (어드민) — idle TTL 등
GET    /v1/admin/settings/llama_server.idle_ttl_seconds
PUT    /v1/admin/settings/llama_server.idle_ttl_seconds   { value: "60" }
```

## 자동 복구 (Auto-Recovery)

```
background loop (10s):
  for process in registry:
    if !process.is_alive():
      log warn "process {pid} died, restarting"
      restart(process.config)  // 모델 이미 로컬에 있으므로 30s 내 복구
```

## Completion Criteria

- [ ] llama-server 바이너리 자동 설치 (GitHub Releases, 로컬 + 원격 노드)
